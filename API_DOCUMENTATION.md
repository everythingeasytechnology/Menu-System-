# API Documentation

Base URL: `/api/v1`

Standard success:

```json
{
  "success": true,
  "message": "OK",
  "data": {}
}
```

Standard validation error:

```json
{
  "success": false,
  "message": "Validation failed",
  "errors": {}
}
```

Authenticated endpoints require:

```http
Authorization: Bearer <access_token>
Accept: application/json
```

## Authentication

### Register

`POST /auth/register`

Auth required: No

Body:

```json
{
  "name": "Owner Name",
  "email": "owner@example.com",
  "phone": "+919999999999",
  "password": "password123",
  "password_confirmation": "password123",
  "business_name": "Cafe Name",
  "business_type": "restaurant"
}
```

Creates an owner user, business, and bearer token.

### Login

`POST /auth/login`

Auth required: No

Body:

```json
{
  "email": "owner@example.com",
  "password": "password123",
  "device_name": "iPhone"
}
```

Returns bearer token, user, and business.

### Logout

`POST /auth/logout`

Auth required: Yes

Revokes current bearer token.

## Business

- `GET /business` - business profile.
- `PUT /business` - update profile.
- `GET /business/settings` - settings/payment flags without secrets.
- `GET /business/status` - current business status.

Update body supports `name`, `type`, `gst_number`, `phone`, `email`, `address`, `city`, `state`, `country`, `opening_time`, `closing_time`, `timezone`, and `status`.

Authorization rule: business is inferred from authenticated user. Users cannot request another business by ID.

```json

  "name": "Rahul Waiter",
  "email": "rahul@example.com",
  "phone": "+919999999999",
  "role": "waiter",
  "status": "active",
  "password": "password123",
```

Edit body:

```json
{
  "name": "Rahul Kumar",
  "email": "rahul.kumar@example.com",
  "phone": "+919999999999",
  "role": "manager",
  "status": "active",
  "password": "newpassword123",
  "password_confirmation": "newpassword123"
}
```

For edit, omit `password` when you do not want to change it.

Status body:

```json

```

Allowed roles:

```text
admin, manager, waiter, kitchen_staff, cashier
```

Allowed statuses:

```text
active, inactive, suspended
```

Delete deactivates staff and revokes active API tokens. Staff APIs are tenant-scoped; one business cannot access another business's staff.

## Orders

- `GET /orders`
- `POST /orders`
- `GET /orders/{id}`
- `GET /orders/active`
- `GET /orders/status/{status}`
- `POST /orders/{id}/status`
- `POST /orders/{id}/items/{itemId}/status`
- `POST /orders/{id}/cancel`

Statuses:

- `preparing`
- `ready`
- `served`
- `completed`
- `cancelled`

New orders start at `preparing`. `completed` is order-level only (set manually once payment/service is fully settled); item statuses only ever move through `preparing` → `ready` → `served` (or `cancelled`).

Authenticated order body:

```json
{
  "table_id": 1,
  "room_id": null,
  "order_type": "dine_in",
  "coupon_code": "SAVE10",
  "payment_method": "cash",
  "items": [
    { "menu_item_id": 1, "variant_id": 2, "quantity": 1 }
  ]
}
```

Status update body (`POST /orders/{id}/status`):

```json
{
  "status": "preparing",
  "items": [
    { "id": 11, "status": "ready" },
    { "id": 12, "status": "preparing" }
  ]
}
```

`status` and `items` are both optional but at least one is required. Send `status` alone to update the whole order (this also cascades that status to every item, same as before). Send `items` alone to update specific items without forcing the order status — the order's overall status is then recalculated automatically from all of its items. Send both to set the order status first and then override specific items afterward. Every `items[].id` must belong to the given order or the request is rejected with 404.

Item status update body (`POST /orders/{id}/items/{itemId}/status`):

```json
{
  "status": "preparing"
}
```

A focused single-item alternative to the combined endpoint above.

Item statuses: `pending`, `confirmed`, `preparing`, `ready`, `served`, `cancelled`.

Updating an item's status recalculates the parent order's overall status from all of its items (e.g. the order moves to `preparing` once any item is `preparing`, and to `ready`/`served` once all items reach that stage). Returns the full updated order. Rejected with a validation error if the order is already `completed` or `cancelled`, or if the item does not belong to the given order.

Authorization rule: order must belong to authenticated user's business.

## Dashboard

`GET /dashboard`

Returns:

- today's orders, and pending/preparing/ready/served/completed/cancelled counts
- today's revenue (paid orders only) and this month's revenue with month-over-month growth percent
- last 5 days revenue trend (`revenue_trend`, one entry per day with orders)
- average order value and average order fulfillment time in minutes (`avg_order_value`, `avg_order_minutes`)
- active/unavailable item counts
- service point status summary (`service_points_status` keyed by status, plus a flattened `service_points_summary` with `total`/`occupied`/`available`/`bill_pending`)
- `recent_orders`: last 10 orders pre-formatted for UI display (`table` location label, `items` as a "2x Paneer Tikka, 1x Cola" summary string, `total`, `status`, `payment_status`, `time`)
- `top_selling_items`: top 5 items this month by quantity sold, with `sold` count and `percentage` relative to the top item
- unread notifications count

## Authorization Rules

- Authenticated user's `business_id` is the tenant boundary.
- Changing IDs in URLs does not grant access to another business.
- Public QR endpoints never expose payment secrets or internal configuration.
- Public order status uses `order_number`, not an internal database ID.
